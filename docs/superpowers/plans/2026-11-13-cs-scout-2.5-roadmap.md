## 0. 一句话结论

2.1.1 的**产品表象是完整的**（双平台、自动/手动、Windows 免 Python 安装、259 项测试），
但支撑它的三层地基——平台抽象、流水线、前端状态——都已经到了「再加功能就开始赔钱」的程度；
而用户真正拿到的分析产出还很薄（回放 + K/D + AWP 率）。

**2.5 的机会不在于再加一个功能，而在于：把「回放工具」升级成「情报报告」，并顺手把地基换掉。**
顺序必须是先地基后功能，否则每个新指标都要在四处重复的互斥逻辑和 38 个前端全局变量里再拧一遍。

## 2. 五层地基的现状

### 2.1 平台层：**没有抽象，只有约定**

- 5E 与完美平台是两个互不相干的 service，各自持有一套调度/状态/取消/重试：
  - 5E：`mark_analysis_started` / `finish_analysis`，无 cancel，`queued`/`ready` 两个 phase 是**死状态**（只在 `fivee_monitor.py:1284,1584` 被引用，从不赋值）。
  - 完美：`request_analysis` / `cancel_analysis`，另一套 phase 词表（`perfectworld_experiment/web_server.py:40-61`）。
  - 两者共有方法只有 4 个，名字都不同 —— 不存在基类或 Protocol。
- **互斥逻辑被复制了 4 份**：`server/web_server.py:146`、`:362`、`:556`、`:695`，外加查询函数 `:160-165`。没有仲裁者。
- **平台判定靠字面量** 6 处（`:69`、`:367`、`:563`、`:417`、`:701`、`:771`），status 合并各写一遍（`:482-499` vs `:626-644`）。
- **结果契约分叉**：完美有 `source`/`target_scope`/`workers`/`timings_s`（`perfectworld_experiment/pipeline.py:603-625`），5E 只有 `map`/`mode`/`results`/`failed`；`/api/results` 只读 5E 目录（`server/web_server.py:859-874`）→ **完美平台的分析结果在前端「最近结果」里不可见**。
- **双向依赖**：`server/web_server.py:99-103` 先 `sys.path.insert(repo_root)` 再 import 完美；`perfectworld_experiment/pipeline.py:51-60` 又反向 `sys.path.insert(SERVER_DIR)` 再 import `parse`/`combat`/`maps`。`server/` 没有 `__init__.py`，所以是**逻辑环**而非导入环——任一侧改目录只在运行时炸，`/readyz`（`server/web_server.py:299-304`）也不检查完美依赖。

> **2.5 的判断**：这是最贵的一笔债。引入第三个平台目前需要改 `server/web_server.py` **20-25 处**、新增一个约 1300 行的 service、再动 `app.js` 18 处平台分支。

### 2.2 流水线层：1615 行，9 类职责

`server/pipeline.py` 1615 行（全文计；非空行 1448）。本文件所有行数均按**全文行数**计，混了：

ZIP 安全解包（`26-247`）、路径与原子写（`47-100`）、`round_id` 偏移（`250-254`）、demo 索引与单飞锁（`260-345`）、磁盘预算与清理（`349-579`）、下载编排（`584-684`）、玩家发现（`692-704`）、normal 双线程流水线（`707-956`）、fast 调度器（`1058-1596`）。

其中**存储与安全策略约占一半**，与分析本身无关。normal 与 fast 之间**没有共享抽象**，已有至少 4 段逐行同构代码并开始漂移：

| 重复段 | normal | fast | 漂移 |
|---|---|---|---|
| `safe_demos` 清洗 | `775-796` | `1005-1026` | — |
| SteamID 回退 | `798-814` | `1028-1045` | — |
| 聚合落盘 | `884-921` | `1169-1201` | — |
| summary | `931-939` | `1580-1596` | 已漂移 |

**资源边界不封闭**：`api_client` 有一个模块级 12 线程详情池（`server/api_client.py:199-202`），在 discovery 里再 fan-out（`:424-432`），HTTP 并发 = 5 ×(12 + 下载池)，**完全不受 `CS_SCOUT_FAST_*` 约束**。

### 2.3 前端层：38 个顶层全局变量，没有状态机

- `server/static/app.js` 有 **38 个顶层 `let`**（已核实），全部共享一个词法作用域；`fiveEUseAnalysisStatus` 只写不读（`:34` 写入，7 处，无读取）。
- 状态更新散落：`setPlatform`/`setScoutMode` 各自改 15+ 个全局再手动 `pollEpoch += 1; clearPollTimer(); resetResults(); poll()`（`:418-506`），`poll` 内部再改 7 个标志（`:1267-1313`）。**平台 × 方式 × 分析模式 × 任务态**四维状态全靠标志组合表达。
- `server/templates/index.html` 798 行里有 **659 行是内联 `<style>`**（`:8-667`），标记部分只有约 130 行。
- **双前端**：`perfectworld_experiment/static/app.js`（152 行）是与主前端并列的第二套实现，跑在自带的 Flask 上（`perfectworld_experiment/web_server.py:326-379` 复制了 `/status`、`/analyze`、`/player`、`/results`、`/maps`、`/icons`）。它**不是死代码**（`README.md:59` 仍文档化独立启动），但不在产品路径上。

好消息（**别改坏**）：单全局 rAF + 时钟驱动、隐藏视图不绘制（`app.js:582-592,899-916`）、全 `textContent`/`createElement` 无 `innerHTML`（`app.js:843-845,927-929`）、SVG 图标首帧 tint 后缓存（`replay.js:42-55`）。这三条是这套手写前端能撑到 1.4k 行的原因。

### 2.4 数据契约层：没有版本，参数无依据

输出的 `player_{domain}.json` **没有 `schema_version`、没有 `window_s`、没有 `tick_rate`**，客户端靠硬编码 20 秒对齐（`replay.js:5`、`app.js:73`、`perfectworld_experiment/static/app.js:143`、`replay_test.html:150-152` —— **四处各写一份**）。

几个隐性契约，任何一个改动都是线上事故：

1. **`round_id = official_num + dem_idx*1000`**（`pipeline.py:250-254`）无 `<1000` 断言，前端当 Set 键用（`replay.js:119,127`）；且 `official_num` 本身只是 freeze-end 事件序号（`parse.py:54`），不是真实局号。
2. **`path` 点长度可变**：有 yaw 时是 4 元组（`parse.py:148-149`），文档写 3 元，客户端兼容 3/4（`replay.js:132`），测试却断言恒为 3（`test_parse_positions.py:35`）。
3. **`awp_rate` 分母含被丢弃的经济局**（`combat.py:60,74-79`），与 `round_count`（`player_json.py:22`）不同源，用户看到的「回合数」和「AWP 率分母」对不上。
4. **参数与设计文档冲突**：`EQ_BUY_MIN=2000` 个人装备门槛（`config.py:48`、`parse.py:102`）**推翻了** `docs/superpowers/specs/2026-06-24-cs-scout-2.0-replay-design.md:75,139` 的「队均 3800 / 3 类」设计；`WINDOW_S=20` 与同文档 `:78` 的 45 秒冲突。两个值都没有分布依据，`EQ_FULL_BUY` 已成死常量。
5. **`transform` 在 JS 里重算**（`replay.js:112-113`），Python 侧无跨语言一致性测试。

### 2.5 交付层：手工发布，安装 5-10 分钟

- **版本号硬编码**：`windows/Build-Windows-Release.ps1` 里 8 处，外加 `README.md`、`server/templates/index.html:6`（还写着 `CS-Scout 2.1`）、`windows/README-PLAYER-ZH.md`。2.5 漏改一处就是错包或构建失败。
- **无自动更新、无版本可见性**：全仓无 version/update 路由，用户从 2.1.1 升到 2.5 只能手工换目录。
- **安装失败不可诊断**：pip 无镜像、无 wheelhouse、哈希未锁（`windows/Install-CS-Scout.ps1:501-506`），失败只报英文退出码；首次安装 ZIP 10-20MB + Python 30MB + wheel 50-60MB，落盘 350-400MB，**5-10 分钟**。
- **CI 不发布**：`ci.yml` 只有 test job，`permissions: contents: read`（`:8-9`），GitHub Release 靠手工上传。
- **真实解析测试在 CI 上 0 覆盖**：10 个测试依赖 328MB 的 fixture demo 且不入库，缺失即 `pytest.skip`（`ci.yml:55-59`、`test_combat.py:58`、`test_parse_*.py:7-8`）。
- 好的一面（**别改坏**）：`PORT=0` + token/PID 绑定的原子启动 JSON、命名 mutex 单实例、Python 下载 SHA-256 + Authenticode 双校验、程序与数据分离（`%LOCALAPPDATA%\CS-Scout`）、严格 allowlist + 原子发布 + 回滚。

### 2.6 文档债

`CLAUDE.md` 仍完整描述 **2.0 的单平台架构**：通篇没有 `fivee_monitor.py`（2260 行，5E 自动模式的核心）
和 `perfectworld_experiment/`（完美平台整条链路），端点表也漏了 `/api/pwa/*`、`/api/5e/*`、`/api/cancel`、

## 3. P0：先修的缺陷（正确性 / 稳定性 / 安全）

> 这些与 2.5 功能无关，但会直接表现为「用户点不动了」，建议无论 2.5 怎么定都先修。

| ID | 缺陷 | 位置 | 用户可见后果 | 修法 | 规模 |
|---|---|---|---|---|---|
| **D1** | 完美自动分析的 token **无兜底释放** | `web_server.py:755` 占用，只在 `_watch_pwa_analysis` 的 `finally`（`:177-178`）释放；watcher 线程 `start()` 失败只 `log` 不释放（`:781-789`） | 之后**每一次**分析请求都返回 409，只能重启服务 | watcher 加超时 + start 失败即释放 + 改成 contextmanager | 小 |
| **D1b** | 同一个 watcher **没有超时**：若 service 永远停在 `queued`，循环永不返回 | `web_server.py:168-178` | 同上，且概率比线程启动失败更高 | 加最大等待时长 + 异常即释放 | 小 |
| **D2** | 取消只在**阶段边界**生效 | `pipeline.py:583-597`（`ProcessPoolExecutor` 要等已提交解析跑完）、`api_client.py:718`（下载循环无 cancel 检查） | 用户点取消后可能再等几分钟，界面像卡死 | 进度回调里检查 cancel event + `shutdown(cancel_futures=True)` | 中 |
| **D3** | 磁盘预算**每 64KB chunk 持锁 `os.walk` 全目录** | `pipeline.py:473`（在 `self._lock` 内）由 `:488-509` 的进度回调每 chunk 触发 | 并发下载被**串行化**，「快速模式」名不副实 | 缓存目录尺寸 + 按时间/增量节流 | 小 |
| **D4** | normal 模式**每个 demo 二次开库**算 combat | `pipeline.py:870`、`:888` | CPU 近半浪费，normal 模式慢得没必要 | 复用 `parse_demo_with_context` 的 context | 小 |
| **D5** | 环回请求**只信 `remote_addr`**，不校验 Origin/Host；`/api/pwa/analyze` 不读 body、无自定义 header | `web_server.py:443-450`、`:750-789`（对比 `:736` 有 `X-CS-Scout-Request`） | 同机反向代理或 DNS rebinding 可读状态；跨站表单可直接 POST 触发分析 | 统一校验 Origin/Host + 全部写操作要求自定义 header | 中 |
| **D6** | 双实例共享 `DEMO_DIR` **会互删正在解析的 `.dem`** | `pipeline.py:433`、清理逻辑 `:571-579` | 双开即数据损坏 | 服务层加 lockfile（启动器的 mutex 只保护 Windows 路径） | 小 |
| **D7** | 失败原因被吞成 `[]`，上层只报「demo 下载全部失败」 | `pipeline.py:671-684`、`:825` | 用户无法自助排障 | 结构化 `reason_code`（预算/URL/网络/解析） | 中 |

## 4. 三条主线（2.5 的范围候选）

### 主线 A｜情报深度：从「回放」到「情报报告」

把已有的数据榨出战术结论，**几乎不需要新的数据源**：

| 子项 | 数据来源（现成） | 用户得到什么 |
|---|---|---|
| A1 回合胜负与比分 | `round_end.winner` + 目标 `side`（当前被丢弃） | Buy 局胜率、CT/T 攻防偏好 |
| A2 经济画像 | `current_equip_value` 全程采样 + `inventory` 解析 | 对手爱 eco 还是强起、道具/护甲构成 |
| A3 首杀 / 首死倾向 | `player_death.tick` - `fe_tick` + `attacker_steamid` | 谁是开路人、谁先掉 |
| A4 可配置时间窗 | `WINDOW_S` 参数化 + 关键事件补采样 | 不再只看开局 20 秒 |
| A5 团队视图 | 现有引擎已支持多 player 叠加（只在手枪局用了） | 5 人同屏看协同与交叉火力 |
| A6 导出情报卡 | 纯前端 canvas 合成 | 一张能发给队友的图 |

- **可感知收益**：最高。这是唯一让「2.5」听起来比「2.1.2」更像一个版本的方向。
- **成本**：A1-A3 便宜（解析层已有一半数据）；A4 涉及 JSON 体积与解析耗时；A5/A6 是交互与前端工程。
- **风险**：指标口径一旦定错，用户会拿着错结论去做赛前准备——必须先写清口径文档再实现。

### 主线 B｜架构收敛：把地基换掉

- B1 平台适配层：`PlatformAdapter` Protocol（`claim`/`release`/`snapshot`/`cancel`）+ registry，把 4 处复制的互斥收敛成 1 处。
- B2 `perfectworld_experiment` → `platforms/perfectworld`，`fivee_monitor` → `platforms/fivee`，消除 `sys.path` 双向 hack 与「实验」这个名不副实的包名。
- B3 拆 `pipeline.py`：`demo_store.py`（ZIP + 索引 + 预算 + 下载）+ 调度器，目标 < 700 行。
- B4 拆 `fivee_monitor.py`（2260 行、6 职责）为 parsing / cdp / windows_system / launcher / service，先搬纯函数，让 `_resolve_match`（145 行、四层重试、零单测）可测。
- B5 normal/fast 共用 `discover_player()` 与统一落盘，去 ~120 行重复，止住漂移。
- B6 前端 state store / reducer，删只写标志，把四维状态显式化；拆 `style.css`。
- B7 契约版本化：JSON 加 `schema_version`/`window_s`/`tick_rate`/`stat_rounds`，`round_id` 加断言。

- **可感知收益**：用户直接感知弱（但 D1-D7 修复会明显感知），**它买的是 2.6/3.0 的速度**。
- **成本**：最贵的一档。
- **风险**：重构期不能影响正在用的发布版；需要行为无回归的验证手段（当前前端测试很薄）。

### 主线 C｜交付体验

- C1 版本单一源：`VERSION` 文件驱动 Build / README / UI / deploy，消除 8 处硬编码。
- C2 自动更新**提示**（不做静默执行）：`/api/version` + 读 GitHub Releases，仅提示 + 跳转下载。
- C3 安装提速与可诊断：`CS_SCOUT_PIP_INDEX_URL` 镜像、wheelhouse、`--only-binary=:all:`、安装日志、中文可操作错误、磁盘预检。
- C4 CI 自动发布：`windows-latest` 跑 Build + Verify + PSScriptAnalyzer，tag 时自动建 Release。
- C5 文档对齐：重写 `CLAUDE.md` 到 2.5 架构（见 2.6）。

- **可感知收益**：中高（安装 5-10 分钟 → 2-4 分钟、失败能自助、能发现新版本）。
- **成本**：最低的一档，大部分是 PowerShell 与 CI。
- **风险**：低。唯一要克制的是**别做静默自动更新**——没有代码签名与权限模型时，风险高于收益。

## 5. 推荐：先地基、再头牌、交付穿插

理由：主线 A 的每一个新指标都要落在 `player_json` 契约和 `state` 状态机上。若不先做 B1/B7，A1-A6 会被迫在「四处重复的互斥」和「四维标志组合」里再实现一遍，**返工成本大于先做的成本**。C 全程开销小、随时可插入。

```
M0 止血 ──▶ M1 地基 ──▶ M2 情报 ──▶ M3 发布
 (2-3d)     (8-12d)      (15-20d)     (5-8d)
```

| 里程碑 | 内容 | 验收标准 | 估时 |
|---|---|---|---|
| **M0 止血** | D1、D1b、D2、D3、D4、D5；`VERSION` 单一源；JSON 加 `schema_version`/`window_s`（纯新增字段，旧客户端不受影响） | 全量 pytest 绿；新增 3 个回归测试（token 兜底、取消及时性、预算节流）；打包脚本只从 `VERSION` 取版本 | 2-3 人日 |

## 6. 需要你拍板的决策

1. **2.5 的头牌押在哪？** A 情报深度 / B 架构收敛 / C 交付体验 / 你另有目标（换 UI？支持第三平台？多人协作？）
2. **VPS 部署路径保留吗？** 保留意味着两套制品、两套鉴权、两套数据路径的长期维护成本（C 里可以把它们统一成一份制品）。
3. **`perfectworld_experiment` 允许重命名/迁移吗？** 会打断仍在使用独立启动路径的脚本或分支——`README.md:59` 还文档化着这个用法。
4. **回合采样窗口怎么办？** 继续固定开局 20 秒（现状）/ 参数化随包配置 / 扩到全场（JSON 体积与解析耗时显著上升）。
5. **要不要团队视图 + 导出情报卡？** 这是 M2 里产品交互改动最大的部分，也最可能是「2.5 有面子」的地方。
6. **版本节奏？** 2.5.0 一次到位，还是先发 `2.1.2` 止血 + `2.2` 地基 + `2.5` 功能（用户感知更平滑，但要维护三条版本线）。
7. **有外部约束吗？** 比如近期要给队友/客户演示、要开源推广、要支持第三平台——这些会直接改变优先级。

## 7. 明确不做（2.5 范围外）

- **换 Vue/React**：单页 1.4k 行、无路由、无构建链，换框架的收益抵不上风险。
- **静默自动更新**：无代码签名与权限模型时，风险高于收益；只做「提示 + 人工确认」。
- **多 Gunicorn worker**：任务状态与单飞锁在进程内，加 worker 会破坏正确性（`deploy/README.md:16-18`）。
- **把 demo / 地图资源提交进 Git**：328MB fixture 与地图二进制不适合入库。
- **为「本地免密钥」放开公网访问**：`LOCAL_MODE` 的回环限制是有意的安全边界。
