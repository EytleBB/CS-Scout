## 0. 一句话结论

「平台不可用 / 读不到对局」不是玄学，是两个可以精确定位的断点：

1. **5E**：我们只等 5E 推送某种结构的帧，并且只在里面递归找 `game_ctx` 这个键。
   平台一改推送信封、换 Comet 传输层、或把名单页换到另一个域名，我们就**零数据且不报警**。
2. **完美平台**：真正的原因是**日志监听循环被「官方组件就绪」挡在门外**——
   没装 DLL 就永远进不到读日志那一步，而且组件检查还会把 phase 强行改写成 `setup_required`，
   把已经识别到的对局一起抹掉。**已于 2026-11-13 定位并修复**（见第 10 节）。

而「战前面板」所需的数据，**平台侧早就给全了**。cmh 之所以信息密度高，不是因为它算得多，
而是因为它把平台算好的东西**读全了**：完美平台的开局 JSON 里就带 7 维雷达、赛季 Rating、近 10 场、完美战力。
我们现在的路线是「下载 100–200MB demo 自己算 K/D」——又慢又薄。

**所以 2.5 的正确顺序是：先修读取（拿到平台的全量数据）→ 战前面板自然就有数据了 → 再谈工程优化。**

## 1. 用户症状 → 技术根因

| 用户反馈 | 真实根因 | 代码证据 | cmh 的解法 |
|---|---|---|---|
| **5E 读不到对局** | 只订阅 WS 推送帧，只在 `current.game_ctx` 里递归找名单；target 只接受 `https://view-arena.5eplay.com/*` | `server/fivee_monitor.py:1929`（只处理 `Network.webSocketFrameReceived`）、`:289-291`（只认 `game_ctx`）、`:1569`（硬 host 过滤） | 在 **CDP Network 层截获客户端自己发出的已鉴权业务请求**，URL 按**路径片段**白名单匹配（`platform_5e_cdp.rs:358-391`、`platform_5e_sink.rs:24-27`） |
| **5E 偶发「未运行」** | 只探测固定端口 9222，被占或多开时误判 | `fivee_monitor.py:86-91` | 端口三态判定（Available / CdpActive / Occupied）+ 失败向 +1…+40 顺延（`platform_5e_launch.rs:194-211,296-330`） |
| **完美平台常不可用** | **元凶（已修）**：日志监听循环被「组件就绪」门控，没装 DLL 就永远不读日志；且组件检查会把 phase 改写成 `setup_required`，抹掉已识别的对局 | `perfectworld_experiment/web_server.py:176-179`（`if not signer["ready"]: continue`）、`:88-92`（phase 覆写） | cmh 完全不看组件，只读日志 |
| **完美手动查玩家依赖重** | DLL 签名桥 + `csc.exe` 现编 x86 桥，失败码 5 种（**只影响手动查玩家，不影响自动识别**） | `native_signer.py:280-327` | 不需要（无登录态依赖） |
| **完美读到了但信息很薄** | 只解析 4 个字段，`playerlist_extrainfo` 整块丢弃 | `current_match.py:107-181` | `parseExtraInfo` 二次 `JSON.parse` 后展开全量（`match-parser.ts:46-76`） |
| **日志读着读着就断了** | 每秒重读最近 3 个文件（O(文件) 而非 O(增量)），无目录自愈 | `current_match.py:276-304,307-331` | 按 offset 增量 tail + 行缓冲 + 截断/换文件检测 + 祖先目录监听（`log_watcher.rs:405-457,275-281`） |

**关键更正**：完美平台的日志解密**不需要** DLL 签名桥。cmh 的解密是**单字节 XOR**
（`bytes[i] = hex ^ ((42 + 3i) % 255)`，`log-decrypt.ts:1,9`），密钥是硬编码常量、不从客户端推导，
**不会随客户端更新失效**。CS-Scout 的 `current_match.py:60-73` 已独立实现同一公式。

## 2. 能力对比矩阵

| 维度 | cmh | CS-Scout 2.1.1 | 差距 |
|---|---|---|---|
| 5E 对局发现 | 截获客户端 batch 请求响应 | 解析 WS 推送 `game_ctx` | **抗改版能力差一个数量级** |
| 5E 端口/UAC | 三态检测 + 顺延；不提权，要求「先退出客户端」 | attach 语义 + `runas` 提权兜底 + listener 归属校验 | 各有胜负（见第 5 节） |
| 5E 玩家数据 | `user/info` + `elo/info/batch` + `map-ext/batch` → ELO/RWS/地图胜率/近况 | 只 `user/info`（`:46`、`:492`） | **缺 2/3** |
| 完美对局发现 | 日志 tail（增量） | 日志轮询（全文件重读）**且被组件门控（已修）** | 地基相同，效率差 |
| 完美玩家数据 | `playerlist_extrainfo` 全量 + 7 维雷达 + 近 10 场 | 4 个字段 | **差一个数量级** |
| 完美手动模式 | 不需要（无登录态依赖） | 需要 DLL 签名桥 | **稳定性差** |
| 战前面板 | 完整（队伍表 + 对比 + AI） | 无 | 全新 |
| demo 深度分析 | 无 | 有（路径/道具/死亡/回放） | **CS-Scout 独有优势** |
| 本地安装成本 | Tauri 包，无 Python | 需装 Python 3.12 + ~350MB 依赖 | CS-Scout 更重 |

### 环境约束：开发机是 QEMU 虚拟机（2026-11-14 确认）

| 项 | 实测值 | 影响 |
|---|---|---|
| CPU | 2 逻辑核 | `FAST_DOWNLOAD_WORKERS` = 6，`FAST_PARSE_WORKERS` = **1** |
| 内存 | 8 GB 总量 / 空闲 1.9 GB | 内存闸门 `(1869-1024)//2048 = 0` → 同样压到 **1 个解析进程** |
| 磁盘 | C: 可用 82 GB | 当前 30 GB 缓存上限可满足，但跑真实 demo 批量测试会很快吃满 |
| 平台客户端 | 无 5E / 无完美平台 / 无 CS2 | **两个平台的端到端验证在本机做不了** |

**因此**：

1. 本机跑出来的耗时**不代表用户机器**。用户多在 8-16 核、16-32 GB 内存的游戏机上，
   但 `_DEFAULT_FAST_PARSE_WORKERS` 被写死为「CPU>2 就是 2」，**核数再多默认也只有 2 个解析进程**。
   这是一个应当修正的默认值（建议 `min(4, max(1, cpu//2))`，再交给内存闸门收敛）。
2. 轨迹功能的「暖场窗口内出结果」在本机不可能验证；本机只能验证**正确性**，不能验证**时延**。
3. 本机测试不要下载真实 demo 批量跑，避免撑爆 VM 磁盘与内存；解析正确性用合成数据覆盖。

### 5E 截获：尚未用真实抓包验证的假设（M0-V 实测清单）

以下全部来自 cmh 文档与代码推断，**没有任何一条经过真实 5E 客户端验证**：

1. 四条 URL 路径（`/player/map-ext/batch`、`/player/elo/info/batch`、`/api/user/info`、
   `/api/data/match/`）仍与 2026-06-16 的样本一致；路径本身改名则会静默 0 命中（只会看到 `ignored` 上升）。
2. 这些请求由 `view-arena.5eplay.com` 的 page target 发出；若改由 worker/iframe 发出，当前连接看不到（target 兜底未做）。
3. `loadingFinished` 后立刻 `getResponseBody` 仍能取到已鉴权 XHR 的 body。
4. body 为 UTF-8 JSON 文本（base64 分支只按 CDP 规范实现，真实样本未出现）。
5. `requestWillBeSent.request.postData` 对三个 batch POST 一定存在且为 JSON。
6. 响应字段结构（`code/data`、`message` vs `msg`、`specialData` 为嵌套 JSON 字符串等）与文档一致。
7. `/api/data/match/` 不会同时命中其它列表接口；`match_code` 恒为路径最后一段。
8. 事件顺序、重复回包、`loadingFailed` 等防御性分支的真实 CDP 行为未观测。

**结论**：切换识别逻辑（M0-2）之前，必须先做一次真实抓包核对以上 8 条；否则只是把「解析推送帧」换成了「解析可能不存在的响应」。

### 时间线：完美平台失效的**真实原因**是客户端更新（用户确认）

**结论订正**：不是 CS-Scout 的改动把功能弄坏的，而是**完美平台客户端更新**导致原有读取方式失效。
`2.1.1-alpha.1` 里的「自动查找组件 / 网页选择安装目录」是**对这次更新的应对**（客户端装到新位置），
而不是故障原因。此前把它写成「回归」是判断错误。

git 记录（只用于说明各版本的代码形态，不代表因果）：

| 版本 | `_watch_loop` 行为 | `request_analysis` 行为 |
|---|---|---|
| **2.1.0**（`2ebd2bb`） | 直接 `wait_for_current_match()` 读日志，**没有组件检查** | 只要 phase 是 `awaiting_confirmation` 就接受 |
| **2.1.1-alpha.1**（`fc4e5b5`） | 新增 `refresh_signer_status()` + `if not signer["ready"]: continue` | 新增同样的组件门控 |
| 2.1.1 正式版 | 同上（未回退） | 同上 |

**本轮修复的价值与边界**：
- 有价值：识别不再被组件可见性挡住 → 只要日志格式没变，识别就能恢复。
- **不充分**：如果客户端更新同时改了日志路径 / 加密 / payload 结构，识别仍然拿不到数据。
  修复的是「不必要的门控」，不是「上游变更造成的格式失配」。

**待确认的四种可能**（只能靠真实数据判断，不能靠代码推断）：

| 可能 | 症状 | 适配难度 |
|---|---|---|
| A 日志目录或文件名变了 | 找不到 `pvpClient*.log` | 小：放宽搜索 |
| B 日志加密变了 | 解出乱码 | 中大：需重新逆向 |
| C payload 结构变了 | 能解明文但认不出对局/名单 | 中：改解析 |
| D 只有签名组件位置变了 | 识别正常、分析失败 | 小 |
